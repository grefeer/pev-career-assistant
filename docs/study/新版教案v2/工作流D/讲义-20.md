# 第 20 章：一次对照实验，不能把成功率讲成全部真相

## 小剧场：一边更快，一边更可解释

小林把同一批问题交给当前自研 PEV 和 deepagents 对照实现。主 PEV 有一题模型乱码，重试后进入 `waiting_user`；另一题撞到验证码，属于外部阻断；第三题因没有真实 API key 被 skip。deepagents 在一轮上更快，但用了更多 turns 和 replans。面试官问：“谁赢了？”工程化回答不是看一个百分比，而是把状态、成本和故障原因放回同一份评测记录。

## 术语出生证：测试名词来自事故边界

`unit test`（单元测试）叫 unit，因为只隔离一个函数/类，代码在 `tests/unit/`，如 `test_agent_model_gateway.py`；它不是真实 MySQL、DeepSeek 或生产部署。`integration test`（集成测试）叫 integration，因为把模块与依赖接起来，代码在 `tests/integration/`，如 `test_object_store.py`、`test_pev_live_end_to_end.py`；它不是生产流量。`e2e` 是 end to end（端到端），代码在 `tests/e2e/` 和 live 验收；它从用户目标走到交付，不是所有分支覆盖。

`eval` 是 evaluation（评测），入口是 `tests/question/eval_runner.py` 的 `run_question()`；它用问题集观察行为、状态和成本，不是单个固定输出测试，也不是主观打分。评测预算也影响结论：`DEFAULT_BUDGET` 现为 36 turns / 64 tool calls / 2 replans / 600s 墙钟 / 256 次模型请求 / 2M 输入 token，并把自动恢复次数开到 2——预算数值要随代码核对，不能背旧值。

这里有三个容易同名混淆的层次。第一层，默认生产运行时是 `backend/app/services/agent_runtime/` 的 adaptive PEV，由 `PlannerAgent`、`ExecutorAgent`、`VerifierAgent` 和 `AgentRuntime` 组成。第二层，生产 `ExecutorAgent.run()` 可以在**一个 PEV Step** 内委托 `DeepExecutorAgent`；后者内部使用 `create_deep_agent`，但仍受外层 PEV 的计划、预算和验收约束。第三层，`backend/app/services/deepagents_runtime/` 是独立的平行/比较实现，对照入口是 `eval/compare_runner.py`，不是默认生产入口。旧 Supervisor / Web Navigation Agent / worker 管线已经退役删除，不能拿来解释今天的 `job-discovery`。

指标名字也要有出处：`RunMetrics` 包含 `status`、`steps`、`turns`、`tool_calls`、`replans`、`wall_clock_s`、`error_code`。`waiting_user` 是可恢复的人机边界，不是 failed；turns、replans 和耗时描述过程成本，不单独代表质量。

最容易误读的是历史字段名 `RunMetrics.tool_calls`。PEV 对照腿实际统计的是“`payload_json` 含 `tool` 的持久化 Event 数”：`sum(1 for event in events if (event.payload_json or {}).get("tool"))`，更准确应理解成 `tool_event_count`，而不是严格工具调用数。它会**漏计**没有对应 Artifact/Event 的成功调用以及生产 DeepExecutor 内未逐项持久化的调用；一次批量 observation 若生成多个 pages/details Artifact/Event，也可能**多计**。独立 deepagents 对照腿则直接读取 `DeepAgentsBudgets.tool_calls_used`。两个数名字相同、来源不同，且 PEV 一侧存在双向失真，只能作带注释的观察，不能包装成精确成本横比。

## 成功/失败慢动作：同一事故如何落到报告

成功路径：

1. `unit` 用假模型先验证 schema、乱码、预算和状态分支；通过只说明零件规则正确。
2. `integration` 接真实依赖，写出对象存储/数据库边界；`e2e` 从自然语言目标跑到 Run 与四类 Artifact，结果仍从 MySQL 的 steps、turns、artifacts、events 读取。
3. `eval_runner.run_question()` 为每题创建真实 AgentRun，并汇总状态、错误码、turns、token 用量和数量后返回 record；2026-08 起每题还带 `auto_recovery_count`（该 Run 的 `run_auto_recovered` 事件数，直接统计 Harness 自动恢复了几轮）；CLI `main()` 才把逐题 JSON 原子写入输出目录。同题才可进入比较。
4. `compare_runner` 让主 PEV 与独立 deepagents 实现跑相同问题，并记录状态、steps、turns、历史字段名 `tool_calls`、replans、wall-clock 和 error code；报告必须注明 PEV 的其实是可能漏计也可能多计的 Event 数，且两腿口径并不相等。

失败/非成功路径：

1. unit 全绿但真实 API key 缺失：live E2E 是 skip/未执行，不是通过。
2. 公开页面验证码：记录外部阻断或 `waiting_user`，不是模型代码失败；不能绕过。
3. 乱码重试耗尽：`invalid_model_response`，Runtime 可把 Run 放 `waiting_user`；它和 `tool_budget_exhausted` 的预算失败、验证失败不是同一个原因。
4. A 成功但 12 turns/8 个带 tool 的 Event/3 replans，B 成功但 3 turns/2 个预算内工具调用/0 replans；由于中间一项不是同一口径，不能直接据此判定谁调用更少。deepagents 一轮更快也不足以替换主 PEV，必须看多题、同边界、同预算和长期故障分布。

## 打开源码只看一个入口：`tests/question/eval_runner.py`

先从 `backend/app/main.py` 确认默认装配的是 PEV；再读 `backend/app/services/agent_runtime/executor_agent.py` 与 `deep_executor.py`，看生产 Executor 如何在一个 Step 内委托 deep agent。最后读 `tests/question/eval_runner.py` 与 `backend/app/services/deepagents_runtime/eval/compare_runner.py`：前者汇总 PEV，后者定义独立对照和 `RunMetrics`。这样才能把“生产内嵌执行器”和“平行对照运行时”分开。

## 术语说错会造成什么工程后果

把 skip 算通过，会让团队以为真实依赖已验证；把 waiting_user 合并进 failed，会把可恢复人机边界误报成代码故障；只报成功率，会隐藏高成本重试和 evidence blocked；把 PEV 的 Event 数当作严格调用数，既可能漏计也可能多计，再与 deepagents 的预算计数直接相除，会制造虚假的成本精度；把 deepagents 更快写成“已取代主 PEV”，会混淆默认入口、内嵌执行器和独立对照。

## 停顿题

1. API key 缺失时，unit 绿和 live E2E 的关系是什么？
2. `waiting_user` 为什么不能和 `failed` 合并？
3. 成功率相同但 turns/replans 差很多，面试时应如何判断？

## 30 秒回答

“默认生产入口是 adaptive PEV；它的 Executor 可在一个 Step 内用 DeepExecutor，但独立 `deepagents_runtime` 只是评测对照腿。评测同时保留 status、steps、turns、历史字段 `tool_calls`、replans、wall-clock 和 error code；skip、外部阻断、waiting_user 与 failed 不能混成一个数。PEV 的 `tool_calls` 实为可能漏计也可能多计的 tool Event 数，独立腿则读预算计数，两者不能做假精确的成本横比，更不能凭一轮更快替换当前 PEV。”

## 记忆钩子

“测试看层级，评测看长期；成功率之外，还要问谁等待、花几轮、为什么失败。”
