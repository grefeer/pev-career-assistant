# 第09章 预算和恢复像工地账本

## 小剧场：断电以后，不从模型记忆开始

林岚的岗位证据已经保存，Verifier也通过了匹配步骤。现在轮到下一个 Step的 Executor生成简历改写建议，服务器进程突然断电。恢复后，系统不能说“我记得模型刚才想到了一个 URL”，也不能把已经用掉的额度重新发一遍。先问动作问题：哪些记录已经提交？哪个角色从哪里接棒？哪些权限永远不回来？

## 术语出生证：账本记录什么，恢复不是什么

**turn** 在这里是一次 PEV角色交还给 Runtime的外层决策记录，不是每次物理模型请求都必然独立落库。代码落点是 `AgentTurn`、`AgentTurnBudget` 和 `runtime.py` 的 decision trace。旧的确定性 Executor循环里，一次 `call_tool` 决策既是一个 turn也可被工具决策计数；但生产 DeepExecutor内部会多次调用模型和工具，整个 `DeepExecutorAgent.run()` 生命周期只形成一个外层 PEV turn，内部模型调用仅以 `internal_model_calls` 汇总在 trace metadata中。

**tool budget** 运行中仍约束真实 Tool handler调用；`ToolCallBudget`记录当前进程内的 used和maximum，重复成功调用被去重时不再次消费。但是生产 DeepExecutor的内部工具调用不会逐个持久化成 `AgentTurn.decision_json.action == "call_tool"`；数据库恢复计数只能看见外层 decision trace。因此不能声称进程中断后一定能完整重建 DeepExecutor已经花掉的内部工具额度。

**replan** 是 re（重新）加 plan（计划），指 Planner重新生成计划。初版计划不算一次额外 replan；Runtime用已经落库的 Plan revision计算 `max(0, revision - 1)`。这个名字强调改变计划结构，不是把原动作盲跑一遍。

**wall-clock** 是“墙上时钟”，指真实经过的时间窗口，不是模型思考了多少轮。Runtime用 `time.monotonic()`生成 deadline；时间到期是资源暂停，通常把 Run或 Step送到 `waiting_user`。新的 resume可以重新计算时间窗口，但不会让 turn、tool、replan的已用数倒退。

**checkpoint** 是“检查点”，这里准确说是提交安全边界：已经知道的计划、步骤、事件、外层决策摘要和工具证据被提交后，系统才把它当作可恢复事实。`AgentRuntime._checkpoint()`只是生命周期边界上的 `db.commit()`，不是每次 DeepExecutor内部调用前保存完整 Agent内存；`_build_decision_trace()`为一次外层角色结果创建 AgentTurn。未提交结果和未逐项持久化的内部调用历史都不能被恢复成完整现场。

**resume** 是“继续”，对应用户已经回答的 `waiting_user`。服务层先校验 owner和状态、写入用户回复，Runtime把 Run改回 running，再继续已有上下文。**recover** 是“恢复”，对应服务端仍标为 running但进程中断的 Run；它不需要新回答，只接受服务端的 run id，写 `run_recovery_started`，以持久化证据执行 `replan_from_durable_evidence`。两者都不接受浏览器伪造的“我已经调用过工具”清单。

**auto recovery** 是 Harness 的“有限自动再试”，不是用户手动 resume，也不是进程故障 recover。`AgentBudget.max_auto_recoveries` 默认是 2（schema 上限 5），意思是首次运行后最多再自动尝试两次，共三次机会。它接住的是模型/核验决策类暂停：除了 `need_user`、`verification_failed`、`no_progress_duplicate`、`invalid_model_response`、`wall_clock_budget_exhausted`，白名单还包括执行器自己的握手码 `route_already_consumed`、`candidate_urls_already_supplied`、`target_evidence_not_found`、`target_role_mismatch`、`target_source_mismatch`；暂停契约取自最近一次 `run_needs_user`、`planner_needs_user` 或 `planner_budget_exhausted` 事件，所以 planner 层主动要信息也算。第一次自动恢复把预算上限按 1.5 倍提升并把连续 stall 阈值从 3 放到 4，第二次按 2 倍、阈值放到 5，所有值仍受 schema 最大值限制。

## 慢动作回放：断电前后账本如何接上

### 成功动作剧本：recover从已提交事实重建

**断电前。** 当前角色是 Executor，输入是简历改写 Step和已保存的岗位 Artifact。已经筛选并提交的 observation、Artifact和外层 AgentTurn可恢复；数据库里也有 AgentRun、AgentPlan、AgentStep与事件。若进程恰在 DeepExecutor内部断电，它已做但尚未形成外层 trace或 Artifact的模型/工具动作不能完整恢复。

**恢复入口。** 当前角色先是服务层。它拿着林岚的 user id和 run id查库，确认 owner正确、状态仍是 running；然后 Runtime追加 `run_recovery_started`，策略写明从 durable evidence重规划。Runtime从数据库重新数可见的外层 turn、`call_tool` decision和 Plan revision，并建立新 deadline。这里的 tool计数对旧循环准确，但无法补回未逐项持久化的 DeepExecutor内部调用；这是当前恢复语义的已知边界。

**重新接棒。** 当前角色回到 Planner，输入是原目标、已授权 Skill和已经提交的有界公开证据。它重新生成计划或继续可执行步骤；之后轮到 Executor，最后由 Verifier验收。旧 Artifact可以复用，未提交模型念头不能被包装成 observation。

### 失败动作剧本：硬账用完，不能靠恢复复活

如果 `agent_turn_budget_exhausted` 或 `tool_budget_exhausted`，这是工作权限耗尽，Run进入 failed；终态 Run不能再用 resume强行继续。若普通 REPLAN已经超过 `max_replans`，Runtime写 `replan_budget_exhausted`，同样不能把 revision清零重来。

如果只是 wall-clock到期，情况不同：当前代码把运行送到 waiting_user，提示恢复会获得新的时间窗口。林岚调用 resume后，deadline刷新；数据库里可见的外层 turn、工具决策和 replan计数保留，但不能据此推导所有 DeepExecutor内部消耗都被完整恢复。若等待原因是验证码，resume还需要她提供新信息；若原因是进程断电，recover只从已提交证据重规划。

### 新剧本：系统能自己再试，但不能假装墙不存在

Verifier因为输出格式损坏或一次无进展而把 Run送到 `waiting_user`；planner 层问信息、执行器因缺目标证据/来源不匹配而交回也会落到 `waiting_user`。`AgentRuntime.run()` 随后读取最近一次暂停事件（`run_needs_user`、`planner_needs_user` 或 `planner_budget_exhausted`）的 terminal contract：如果 reason code在自动恢复白名单、`resumable` 没被关闭、证据也没有标记 `blocked=true`，Harness追加 `run_auto_recovered` 事件，带着上次反馈、阶梯预算和更宽的 stall阈值继续同一 Run。默认两次都没解决，状态才保持 `waiting_user` 等人。

如果原因是登录、验证码、反爬，证据契约会标记 blocked；如果是重复计划振荡或硬预算耗尽，也不满足自动恢复条件。这些情况即使“再给模型一次机会”也不会创造新的访问权或额度，因此必须保持人工交接或终态失败。

### 把术语说错会怎样

错误说法是：“checkpoint把 Agent冻结在原地，recover可以恢复模型当时的思路；wall-clock到期会把所有预算刷新；resume和recover都是从头重跑。”这样会把数据库提交边界说成内存快照，也会让恢复重复已经完成的工具工作。

正确说法是：checkpoint是提交安全边界，recover从外层 AgentTurn、事件、计划和 Artifact重建上下文；生产 DeepExecutor内部模型调用只汇总为 `internal_model_calls`，内部工具调用不逐项形成 `call_tool` turn，所以恢复不能完整还原其已用内部预算。resume处理 waiting_user并写人的回答；auto recovery对白名单内的模型/核验/执行器握手暂停（含 planner 层）做最多两次阶梯重试。来源访问阻断、计划振荡和硬预算不会获得新权限。

## 一个源码入口：只打开 `AgentRuntime.run()`，再看两个恢复方法

主入口是 `backend/app/services/agent_runtime/runtime.py` 的 `AgentRuntime.run()`。沿断电剧本读 existing Run怎样取得 `revision`、`consumed_turns`和 `consumed_tool_calls`，再看 `_checkpoint()`与 `_build_decision_trace()`。随后对照 `deep_executor.py`：确认一次 DeepExecutor生命周期只返回一个外层 trace，内部模型数放在 `internal_model_calls`，工具调用没有逐条变成 `decision_json.action == "call_tool"`。最后比较 `resume()`和 `recover()`的状态前提与输入来源。

## 停顿题

1. DeepExecutor内部工具返回后、外层 trace与Artifact提交前断电，这次调用能否由数据库完整恢复？为什么？
2. wall-clock到期后刷新什么、不刷新什么？为什么 turn/tool/replan仍要从数据库计数？
3. resume和recover为什么不能合成一个 API？`_checkpoint()`是否意味着每次工具调用前都保存完整现场？
4. `max_auto_recoveries=2` 是总共运行两次还是“首次加两次”？哪些 waiting_user 原因绝不能自动恢复？

## 30秒回答

“turn是 Runtime看到的外层角色决策；生产 DeepExecutor内部模型调用只汇总为 `internal_model_calls`，内部工具调用不逐条落成 `call_tool` turn，所以 recover不能完整重建其内部预算消耗。checkpoint只提交持久化事实，running进程中断时从 durable evidence重规划；waiting_user可由 resume接回，另有最多两次阶梯 auto recovery（白名单含执行器握手码与 planner 层暂停）。登录、验证码、反爬、计划振荡和硬预算不自动恢复。”
