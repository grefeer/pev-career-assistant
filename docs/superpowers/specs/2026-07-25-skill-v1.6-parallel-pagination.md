# Skill v1.6 - Parallel URL Fetch (detect -> pre-compute -> parallel -> fallback)

Date: 2026-07-25
Branch: master (skill optimization, /goal Phase C)
Predecessor: v1.5 (deterministic dedup filter, `dec5211`)

## Origin

User proposal (verbatim intent): for "网页类 url" (job-listing pages with
URL-keyed pagination), stop reading page-by-page serially. Instead:

1. Route to the job-listing page.
2. If the user gave keywords, look for a search box first; if present, search
   the keywords THEN extract page-by-page; else per-page loop.
3. When extracting page-by-page: click next-page, read the URL (it now carries
   page info, e.g. `current=2&limit=10`); click previous back to page 1, read
   the URL again; diff the two URLs to identify which parameter controls the
   page number (`current`) and which controls page size (`limit`). This lets us
   pre-compute ALL page URLs for PARALLEL fetch.
4. If step 3 errors (3 retries / timeout), fall back to the old per-page serial
   method (v1.5 `--mode click`).
5. Reference Java's thread pool (task queue + multiple threads); does Python
   have an analog?

User instruction: "这种方法仅作参考，请你先评估一下可行性，再优化"
(this is reference only - evaluate feasibility, THEN optimize).

## Feasibility evaluation (the "evaluate" half)

### Where it works (sound)

- **URL-keyed pagination** is the dominant pattern on ATS job boards:
  Mioffice/atsx (xiaomi, bytedance) use `?...&current=N&limit=M...`; mokahr,
  zhiye, and most greenhouse/lever-style boards expose a page/offset query
  param. For these, click-next produces a URL diff that cleanly isolates the
  page param.
- **Detection is cheap**: 2 clicks (next, prev) + 2 URL reads + a query-param
  diff. ~10s. Then N pages fetched in parallel.
- **Python thread-pool analog**: `concurrent.futures.ThreadPoolExecutor` is the
  exact Java `ThreadPoolExecutor` analog (task queue + N worker threads). For
  IO-bound browser fetch, `asyncio.gather + Semaphore` is the more Pythonic
  option. Both are stdlib - no new deps.

### Where it does NOT work (must auto-fallback)

- **"Load more" append (no URL change)**: some moka/feishu-zhiye configs append
  via XHR without changing the URL. Detection sees `url_2 == url_1` -> no page
  param -> fall back to `--mode click`.
- **Opaque/path-based or POST pagination**: if the page param is a path segment
  with no clean numeric increment, or pagination requires a POST body / session
  token, pre-computed URLs won't fetch correctly -> fall back.
- **Anti-bot rate limiting on concurrency**: 4 concurrent requests may trip a
  rate limiter that serial clicks do not. Mitigation: conservative default
  concurrency (4), and if any worker hits a captcha/anti-bot wall, the whole
  mode returns `blocked` (per security hard gate - do NOT keep trying).

### Honest scope of the time win

- v1.6 cuts the **pagination leg** (serial click N times) to parallel wall-clock
  = `ceil(N / concurrency) * per_page`. For xiaomi (16 pages, concurrency 4):
  ~16 serial clicks (~240s) -> ~4 parallel rounds (~60s).
- It does NOT cut the **per-page extraction LLM latency** - that is already
  parallel (one `jd_extractor` sub-agent per page file, v1.4+).
- So v1.6 will NOT achieve the 90% total-time cut the /goal stop-condition
  targets. It is a targeted improvement on the dominant serial leg, with a
  hard auto-fallback so it can never regress completeness on non-URL-keyed
  sites. This is the honest ceiling; the 90% total cut is infeasible for
  multi-page SPAs (recorded in `skill-v1x-optimization` memory).

## Design (the "optimize" half)

### New browse mode: `--mode parallel-fetch`

Self-contained: owns its browser lifecycle (does NOT reuse main()'s pre-opened
sync page). Internally does detect -> parallel OR click-fallback, so the agent
makes ONE call and gets `page_files` either way.

Args (additive):
- `--max-pages N` (cap; default 5, agent sets ~20)
- `--wait MS` (per-page, default 3000)
- `--search-terms` (optional; if given, search first then detect on results URL
  - user step 2; reuses `_perform_search` + `_find_search_input`)
- `--concurrency N` (parallel workers; default 4)
- `--detect-retries` (default 3 - user step 4)

### Flow (`browse_parallel_fetch_mode(url, out_dir, ...)`)

**Phase 1 - detect (sync, own browser):**
1. Launch sync browser, `goto url`, scroll, dismiss consent.
2. If `search_terms`: try search (best-effort - if no box, proceed unfiltered).
3. Read total count via `_read_result_count_text`.
4. `_detect_pagination(page, retries)`:
   a. `url_1 = page.url`
   b. find next-page button (`_find_next_page_button`); if none ->
      `detect=None` (no paginator -> single page; return page 1 only).
   c. click next (timeout 5s, up to `retries`); `url_2 = page.url`.
   d. if `url_2 == url_1` -> `detect=None` (load-more style -> fallback click).
   e. click prev (prev button if findable, else `page.go_back()`); confirm back
      on `url_1`.
   f. diff `url_1` vs `url_2` query params (and path): find the param whose value
      incremented numerically (`1->2`) = `page_param`. Note any `limit`/`size`/
      `pageSize` param = `size_param` (keep its value as `size_val`).
   g. if no numeric increment found -> `detect=None` (fallback).
   h. return `{page_param, size_param, size_val, base_url, total}`.
5. If `detect is None`: **internal fallback** -> `browse_click_mode(page, url,
   out_dir, None, None, max_pages, wait_ms, click_auto=True)` on the still-open
   page (we're back on page 1 after next+prev). Return its result with
   `used_path: "click_fallback"`.
6. Compute `total_pages = min(max_pages, ceil(total / size_val))` (if total
   unknown, use `max_pages`).
7. Pre-compute `urls = [substitute(base_url, page_param, i) for i in 1..N]`.
8. Close the detect browser.

**Phase 2 - parallel fetch (ThreadPoolExecutor + per-worker persistent browser):**
- `ThreadPoolExecutor(max_workers=concurrency, initializer=_worker_init)`.
- `_worker_init` opens ONE persistent headless browser per worker thread
  (`threading.local`) - amortizes browser launch to `concurrency`, not `N`.
- Each task `_fetch_one(url)`: open new context + page on the worker's browser,
  `goto`, scroll, dismiss consent, extract body innerText, close context.
  Check for block keywords in text -> if found, raise `_Blocked` (whole mode
  returns `blocked`, not fallback - per security gate).
- `executor.map(_fetch_one, urls)` -> texts in page order.
- On any non-block exception (network/timeout) after `retries`: abort parallel,
  **internal fallback** to `--mode click` (re-open sync browser, click from
  page 1).
- `_dedup_adjacent(texts)` (sites may echo page-1 content for out-of-range pages).
- `_save_page_files(texts, out_dir)` -> `page_01..NN.txt` (unchanged format).
- Save evidence (page 1 text) + screenshot.
- Return same shape as `browse_list_mode` + `used_path: "parallel"`.

### main() wiring

- Add `parallel-fetch` to `--mode` choices + new args (`--concurrency`,
  `--detect-retries`).
- Bypass cache for `parallel-fetch` (param-dependent, like `click`).
- Dispatch: if `mode == "parallel-fetch"`, call
  `browse_parallel_fetch_mode(url, out_dir, ...)` as a self-contained branch
  (does not use main's `with sync_playwright()` page).

### Agent workflow (single-url-extraction.md step 2)

Replace the click-paginate instruction with:
```
--mode parallel-fetch --max-pages 20 --concurrency 4
```
first. It returns `page_files` either via the parallel path or via internal
click-fallback. The hard limits (at most one parallel-fetch + one click
fallback per URL) still hold - but both now live inside ONE browse call.

### Security gates (unchanged, enforced)

- Never click a login/captcha/anti-bot control (`_CLICK_BLOCK_KEYWORDS`).
- If a parallel worker hits a captcha/anti-bot wall -> return `blocked`, do NOT
  fall back (click would hit the same wall; retrying would be bypass).
- No `task:submit`; browse only reads, never submits.
